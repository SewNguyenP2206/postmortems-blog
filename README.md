## ✨ Features

- 🌑 **Dark DevOps UI** – GitHub-inspired design with severity color coding
- 📋 **Auto-indexed** – GitHub Actions scans `postmortems/` and builds `manifest.json` automatically on every push
- 🔍 **Search & Filter** – Filter by severity (P0–P3), status, services, or free-text search
- 📊 **Stats Dashboard** – Total incidents, P0 count, MTTR, 30-day incident timeline
- 📖 **Full Markdown** – Each postmortem renders rich Markdown with syntax highlighting, tables, TOC
- 🧠 **Knowledge Blog** – Publish AWS, Kubernetes, and DevOps articles from Markdown files in `blogs/`
- 📱 **Responsive** – Works on mobile, tablet, desktop

## 🚀 Getting Started

### 1. Enable GitHub Pages

1. Go to **Settings → Pages**
2. Set **Source** to `GitHub Actions`

### 2. Add a Postmortem

Create a new `.md` file in `postmortems/`:

```bash
cp postmortems/_TEMPLATE.md postmortems/2024-12-01-my-incident.md
# Edit the file, then:
git add postmortems/2024-12-01-my-incident.md
git commit -m "postmortem: my incident title"
git push
```

That's it! GitHub Actions will:
1. Scan `postmortems/` and update `manifest.json`
2. Deploy the updated site to GitHub Pages

### 3. Naming Convention

```
postmortems/YYYY-MM-DD-short-slug.md
```

Example: `postmortems/2024-10-01-database-outage.md`

## 📄 Postmortem Frontmatter

Each `.md` file **must** start with a YAML frontmatter block:

```yaml
---
title: "Service Name – Incident Description"
date: "2024-10-01"
severity: "P0"          # P0 | P1 | P2 | P3
status: "resolved"      # resolved | ongoing | monitoring
duration: "2h 34m"
services:
  - "PostgreSQL"
  - "API Gateway"
author: "Platform Team"
tags:
  - "database"
  - "production"
summary: "One-sentence summary of the incident."
---
```

| Field | Required | Values |
|---|---|---|
| `title` | ✅ | Incident title |
| `date` | ✅ | `YYYY-MM-DD` |
| `severity` | ✅ | `P0`, `P1`, `P2`, `P3` |
| `status` | ✅ | `resolved`, `ongoing`, `monitoring` |
| `duration` | — | e.g. `2h 34m`, `45m` |
| `services` | — | Array of affected services |
| `author` | — | Team or person name |
| `tags` | — | Array of tags for filtering |
| `summary` | — | One-sentence description |

## ✍️ Knowledge Blog

Add one Markdown file per article under `blogs/`. The GitHub Pages workflow builds `blogs/manifest.json` from these files during deployment.

```yaml
---
title: "Kubernetes Requests and Limits"
date: "2026-10-02"
category: "Kubernetes"
tags: ["kubernetes", "resources", "devops"]
author: "Phú Nguyễn"
summary: "A practical guide to CPU and memory requests and limits."
---

Write the article in Markdown below the frontmatter.
```

Use `blogs/_TEMPLATE.md` as a starting point. Supported categories include AWS, Kubernetes, and DevOps; new categories are picked up automatically.

## ⚙️ GitHub Actions Workflow

The workflow triggers on every push to `main` that touches `postmortems/*.md`, `blogs/*.md`, or the site files.

It:
1. Scans `postmortems/` for all `*.md` files
2. Generates the postmortem manifests and `blogs/manifest.json` in the Actions runner
3. Deploys the generated site to GitHub Pages without committing generated files back to `main`

## 📈 Views and Likes API (MongoDB Atlas + Render)

The site is static, so views and likes are stored by the separate API in `api/`. Create a free MongoDB Atlas cluster and a Render Web Service for the API.

### Deploy the API

1. Create a MongoDB Atlas free cluster, database user, and network access rule. For a public Render service, allow Render's outbound addresses or temporarily use `0.0.0.0/0` with a strong database password.
2. Create a Render Web Service from this repository with **Root Directory** `api`, **Build Command** `npm install`, and **Start Command** `npm start`.
3. Add Render environment variables: `MONGODB_URI` (Atlas connection string), `MONGODB_DB=postmortems`, `ALLOWED_ORIGINS=https://postmortems.sewtech.site`, `IP_HASH_SECRET` (at least 32 random characters), and `VIEW_EVENT_RETENTION_DAYS=90` (add any other site origins as comma-separated values).
4. In `js/config.js`, set `POSTMORTEM_API_BASE` to the deployed Render service URL, for example `https://postmortems-api.onrender.com`, then deploy the static site.

For local API development, copy `api/.env.example` to `api/.env`, fill in the Atlas URI, then run `npm install && npm run dev` from `api/`. The API listens on port 3000 by default. Configure `js/config.js` with `http://localhost:3000` while testing locally.

The API exposes `GET /api/health`, `POST /api/posts/:slug/views`, and `PUT /api/posts/:slug/like`. Postmortems and knowledge articles both use these endpoints; knowledge article slugs are prefixed with `blog-`. A page load increments views; each browser gets one toggleable like per article. View events store an HMAC-hashed IP, approximate GeoIP city/region/country, coarse device/browser/OS categories, referrer hostname, and timestamp. The raw IP, full user-agent, full referrer URL, and coordinates are not stored. Location uses the local GeoIP database first; when it has no match, Cloudflare can supply country only if the API is accessed through a Cloudflare-proxied custom domain. A direct `*.onrender.com` request has no Cloudflare location header, so unmatched locations remain null. MongoDB TTL deletes individual view events after `VIEW_EVENT_RETENTION_DAYS` (90 by default); aggregate view totals remain. IP hashes are pseudonymous data, not anonymous data, and the page discloses this collection. Counts are public and are not protected against determined abuse, so treat them as lightweight engagement counters rather than audited analytics. Render's free service may sleep when idle, making the first API request slower.

Never put the MongoDB connection string in frontend JavaScript. It belongs only in Render's environment variables or the ignored local `api/.env` file.
